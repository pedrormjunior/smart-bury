# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Run the test suite: `make test`
  (equivalent to `emacs -batch -l ert -l smart-bury.el -l smart-bury-tests.el -f ert-run-tests-batch-and-exit`)
- Run a single test: `emacs -batch -l ert -l smart-bury.el -l smart-bury-tests.el --eval '(ert-run-tests-batch-and-exit "test-name-regexp")'` (no `-f ert-run-tests-batch-and-exit` here — that would run every test and exit before the `--eval` is reached),
  or interactively via `emacsclient` (see `emacs-skills:emacsclient` — always use `emacsclient`, not `emacs`, for interactive elisp work, byte compilation, or `check-parens`).
- Lint docstrings: `make checkdoc` (runs `checkdoc-file` on `smart-bury.el`; exits non-zero if it reports any warning).
- Byte-compile with warnings as errors: `make compile` (removes the `.elc` afterward).
- Lint package metadata and Emacs-version compatibility: `make package-lint` (runs `package-lint` on `smart-bury.el`, as MELPA does; uses the user's installed `package-lint` via `package-initialize`, or else installs it from MELPA into a git-ignored local `.elpa/`, as in CI).
- CI: `.github/workflows/ci.yml` runs `make test` on Emacs 27.1, 28.2, 29.4, 30.1 (and snapshot, allowed to fail), plus `make compile`, `make checkdoc`, and `make package-lint` on 30.1. Emacs 27.1 is the oldest version `Package-Requires` claims; CI is the only place it's actually tested.
- Try the package interactively, isolated from the user's own init file: `make test-interactively` (loads `smart-bury.el` and `test-interactively.el` under `emacs -Q`; see that file for what it sets up — enabling `smart-bury-mode`/`repeat-mode`, a repeat binding for `smart-bury-kill-current-buffer`, and a few throwaway buffers).
- Explanatory animation (Manim, in `demo/`): `make demo-check` (replays the README cases on the Python model), `make demo-preview` (fast 480p15 render into `demo/smart-bury-demo-preview.mp4`), `make demo` (final 1080p60 render into `demo/smart-bury-demo.mp4`, ~3 minutes). `demo/` is a standalone `uv` project (`demo/pyproject.toml`, Python 3.14, Manim from PyPI); `uv run` creates `demo/.venv` on first use.
- Short intro animation (`demo/smart_bury_intro.py`, ~2:15): `make intro-check` (Manim `--dry_run`: runs the scene without rendering, so every storyboard step's `expect`ed buffer order is asserted against the model; the render targets don't depend on it, since rendering asserts the same), `make intro-preview` (480p15 into `demo/smart-bury-intro-preview.mp4`), `make intro` (1080p60 into `demo/smart-bury-intro.mp4`, ~8 minutes).
- Compare against vanilla behavior: `make test-emacs-defaults-interactively` (plain `emacs -Q` plus only a dark theme from `test-emacs-defaults-interactively.el`; does *not* load `smart-bury.el`).

Important: No need to run tests after every modification, mainly if
they are minor and simple.  Only run tests when a major modification
is performed and we're not sure about the correctness of the code.

## Architecture

Smart Bury is a single-file Emacs package (`smart-bury.el`) that wraps `bury-buffer`, `quit-window`, and `kill-current-buffer` so that repeated invocations cycle through recently-used buffers instead of landing on an arbitrary one.

Core mechanism:
- `smart-bury--commands` lists the package's own interactive commands (used to detect whether a sequence is continuing — see `smart-bury--starts-now-p` below). It starts as the three hand-written basic commands (the constant `smart-bury--basic-commands`: `smart-bury-switch-through-buffers`, `smart-bury-switch-to-other-buffer`, `smart-bury-bury-buffer`) and is extended by `smart-bury--set-wrapped-commands` with whatever `smart-bury-wrapped-commands` generates.
- `smart-bury--starts-now-p` (pure) checks `last-command` against `smart-bury--commands` to detect whether the current invocation continues a sequence or starts a fresh one; `smart-bury--maybe-start-sequence` is what the commands call — on a fresh start it also records the current buffer as `smart-bury--initial-buffer`. `smart-bury--maybe-restart-sequence` adds the other reset condition used by the two switch commands: being back on the initial buffer.
- `smart-bury--initial-buffer` (the buffer active when a sequence started) and `smart-bury--counter` (how many buffers deep into the cycle we are) are the two pieces of global state threaded through a sequence of calls.
- `smart-bury--run-function` is the shared wrapper used by `smart-bury-bury-buffer` and every command generated from `smart-bury-wrapped-commands`: it calls the underlying Emacs function, then — unless this is a fresh sequence — switches through `smart-bury--counter` eligible buffers via `smart-bury--go-through-buffers`, keeping `smart-bury--initial-buffer` in sync with wherever the sequence actually lands.
- `smart-bury-switch-through-buffers` instead calls `smart-bury--go-through-buffers` directly (no underlying Emacs function to delegate to) and increments the counter itself. `smart-bury-switch-to-other-buffer` calls `smart-bury--walk-back` on the first `(1- smart-bury--counter)` buffers from `smart-bury--select-buffers`, landing on the first of them (the initial buffer, or the "other" one on a fresh sequence), then pins the counter to 2.
- The cycling is built from two helpers. `smart-bury--select-buffers` filters a buffer list (normally `smart-bury--buffer-list`, scoped to the selected frame when `smart-bury-same-frame` is non-nil) down to the eligible buffers via `smart-bury--eligible-p` (skipping dead buffers, the minibuffer, internal buffers whose name starts with a space, and buffers already displayed in a window unless `allow-current`), signals `user-error` if none qualify, and returns the first N, wrapping around modulo their count. `smart-bury--walk-back` switches to each buffer of a selection in reverse order, so its first buffer ends up current. `smart-bury--go-through-buffers` selects `smart-bury--counter` buffers, walks back through all but the last, and returns the last for the caller to switch to. The intermediate switches (rather than jumping straight to the final buffer) matter: they are what keep Emacs's real most-recently-used buffer order consistent with the counter, which `smart-bury-switch-to-other-buffer` relies on to land back on the original buffer after a run of `smart-bury-switch-through-buffers` calls.
- `smart-bury-quit-window` and `smart-bury-kill-current-buffer` are not hand-written `defun`s — they're generated by `smart-bury--define-wrapper`, which builds an interactive command named `smart-bury-FN` for each `FN` in the `smart-bury-wrapped-commands` defcustom (default `(quit-window kill-current-buffer)`), reusing `FN`'s own `interactive` spec so it accepts whatever arguments `FN` itself would. The spec is looked up (via `interactive-form`) and evaluated only when the wrapper is called, by `smart-bury--interactive-args`, so `FN` need not be defined when the wrapper is (e.g. a command from a package loaded after Smart Bury); calling the wrapper while `FN` is still not a command signals `user-error`, before any sequence state changes. `smart-bury-bury-buffer` stays hand-written as one of the three basic commands, whose keys come from `smart-bury-keys`.
- Keymaps are split into a user-owned public map and a package-owned parent: `smart-bury-mode-map` (parent `smart-bury--mode-map-generated`) and `smart-bury-repeat-map` (parent `smart-bury--repeat-map-generated`). The public maps start empty and are never touched by the package, so a user's own `define-key` into them survives any customization. `smart-bury--rebuild-keymaps` rebuilds both parents *in place* (`setcdr`) from `smart-bury-prefix-key`, `smart-bury-keys` (alist of COMMAND . single KEY; the key goes after the prefix in the mode map and alone in the repeat map), and `smart-bury--valid-wrapped-commands` (one `[remap FN]` each), plus the fixed `[remap bury-buffer]`. In-place mutation matters because `define-minor-mode` captures `smart-bury-mode-map` *by value*, not via a live symbol lookup — reassigning a keymap variable silently stops taking effect once the mode is enabled (this cost real debugging time). A `smart-bury-keys` entry whose key isn't a single event is skipped with `display-warning`.
- All three options' `:set` functions end in `smart-bury--rebuild-keymaps` (`smart-bury--set-and-rebuild` for the two key options). Since `custom-initialize-reset` runs `:set` *during load*, before later defcustoms exist, the rebuild is guarded to do nothing until all three options are `boundp`; `smart-bury-wrapped-commands` is deliberately defined last so its `:set` triggers the first full build. (`:set-after` would not help here — it only orders `custom-set-variables`, not defcustom evaluation.)
- Setting `smart-bury-wrapped-commands` (via `setopt`/Customize, not plain `setq`) runs its `:set` function, `smart-bury--set-wrapped-commands`, which regenerates the wrapper commands, `smart-bury--commands`, and `smart-bury--valid-wrapped-commands`, then rebuilds the keymaps. An entry that isn't defined yet is wrapped all the same, without a warning. Only an entry known not to be a command (nil, a non-symbol, or a defined but non-interactive function) is filtered out and reported via `display-warning` rather than erroring — only the remaining valid entries get wrapped/remapped/added to `smart-bury--commands`. This matters because this function runs as the defcustom's `:set`, which `custom-initialize-reset` invokes synchronously *while `smart-bury.el` itself is loading* if a saved Customize value already existed (e.g. from a custom-file) before the `defcustom` form ran — an earlier version signaled `user-error` for a bad entry instead, which meant a single stale/renamed command left over in a user's saved config would make `(require 'smart-bury)` itself fail, aborting the whole package (and likely the rest of the caller's init file) over one unrelated wrapper. The check uses `commandp`, not `interactive-form`: the latter loads an autoloaded command's library, which would load every wrapped package as soon as Smart Bury loads. The option's `:type` is `(repeat symbol)`, not `(repeat function)`, which would reject an undefined entry (making `setopt` warn).
- `smart-bury-mode` is a global minor mode whose default bindings are `C-x _`/`C-x M-_`/`C-x M--` (from `smart-bury-prefix-key` + `smart-bury-keys`), plus the remaps described above.
- `smart-bury-repeat-map` lets Emacs's built-in `repeat-mode` repeat a command with a single key once invoked. Every Smart Bury command — the three fixed ones plus every `smart-bury-wrapped-commands` entry — gets `repeat-map` set to it and `repeat-check-key` set to `no` (via `smart-bury--make-repeatable`), so the map arms regardless of which key actually triggered the command.
- Each command reports where it landed through the `smart-bury--report` macro (a macro so `called-interactively-p` is evaluated in the calling command): only when called interactively and `smart-bury-messages` is non-nil, with the "Smart Bury:" label in face `smart-bury-message-prefix`.

The package is GPL-3.0-or-later: `LICENSE` holds the text, and `smart-bury.el`'s header carries the FSF notice.

Tests in `smart-bury-tests.el` use several macros: `smart-bury-test-with-buffers` (creates fresh buffers, resets global state, always kills the buffers afterward), `smart-bury-test-with-buffer-list` (stubs `buffer-list` to a fixed set), `smart-bury-test-with-mode` (enables `smart-bury-mode` for the duration, always disabling it afterward), `smart-bury-test-with-wrapped-commands` (temporarily customizes `smart-bury-wrapped-commands`, always restoring and regenerating the original value afterward), and `smart-bury-test-with-keys` (the same for `smart-bury-prefix-key` and `smart-bury-keys`). Note that `bury-buffer`/`quit-window` pick their target via the *selected window's* own prev/next-buffer history, not via `buffer-list` — so tests for those commands check the counter/initial-buffer bookkeeping invariant rather than the exact destination buffer. The one test that exercises the real (unstubbed) `buffer-list` MRU reordering — `smart-bury-test-switch-through-then-switch-to-other-returns-to-origin` — exists because a prior refactor of `smart-bury--go-through-buffers` passed every other test while silently breaking that invariant; the stubbed-buffer-list tests can't catch that class of regression.

The animation in `demo/` is driven by `demo/smart_bury_sim.py`, a pure-Python model whose methods mirror `smart-bury.el`'s functions one-to-one (single window, `blist[0]` is current; vanilla bury/quit modeled as "move to the end, show the new head"). Its self-check replays README Cases 1–7 and "Why is it smart?" with the same expectations as the `smart-bury-test-readme-*` tests, so any change to the Elisp algorithm should be mirrored there. `demo/smart_bury_demo.py` (scene `SmartBuryDemo`) only draws the model's recorded steps: buffer boxes slide between slots of the "list of all buffers", the window, keys, counter, and "initial" marker update together in `press`. The rendered MP4s are not committed yet; `demo/` is outside the MELPA package (the recipe lists only `smart-bury.el`).

`demo/smart_bury_intro.py` (scene `SmartBuryIntro`) is the short introduction: title cards for the three basic and the wrapped commands, then one continuous five-buffer session (vanilla `C-x b` with minibuffer typing, switching through to the last, switching to the other buffer, breaking a sequence, burying every buffer in turn). Its layout differs from the long demo: the "list of all buffers" at the top with both the current and the other buffer marked, an Emacs frame with a minibuffer (showing repeat-mode's `[Repeat with: M--, _, M-_]` after Smart Bury commands, or the `C-x b` prompt), captions at the bottom. It reuses only `BufferBox`, colors, and fonts from `smart_bury_demo.py`, which it leaves untouched. Each step passes `expect=` with the buffer order it should produce, and the model raises on a mismatch; the storyboard was also replayed against the real package in batch Emacs (with only the demo's buffers eligible) and agreed at every step. The model's `switch_to_buffer` is vanilla `switch-to-buffer`, so it ends a sequence, and `other` mirrors `(other-buffer)`. Note for storyboards: switching through to the last buffer (counter equal to the number of eligible buffers) and then burying it immediately lands on that same buffer. This is expected, not a bug: the bury moves it to the end of the list, and the counter still points to the last position. To show a bury returning to the initial order, work on that buffer first, so the bury is a fresh one.

`test-interactively.el` (run via `make test-interactively`) and `test-emacs-defaults-interactively.el` are separate, non-ERT files for manual sessions under `emacs -Q` (with and without the package, respectively) — not for automated testing.
