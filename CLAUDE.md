# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Run the test suite: `make test`
  (equivalent to `emacs -batch -l ert -l smart-bury.el -l smart-bury-tests.el -f ert-run-tests-batch-and-exit`)
- Run a single test: `emacs -batch -l ert -l smart-bury.el -l smart-bury-tests.el --eval '(ert-run-tests-batch-and-exit "test-name-regexp")'` (no `-f ert-run-tests-batch-and-exit` here — that would run every test and exit before the `--eval` is reached),
  or interactively via `emacsclient` (see `emacs-skills:emacsclient` — always use `emacsclient`, not `emacs`, for interactive elisp work, byte compilation, or `check-parens`).
- Try the package interactively, isolated from the user's own init file: `make test-interactively` (loads `smart-bury.el` and `test-interactively.el` under `emacs -Q`; see that file for what it sets up — enabling `smart-bury-mode`/`repeat-mode`, a repeat binding for `smart-bury-kill-current-buffer`, and a few throwaway buffers).
- Compare against vanilla behavior: `make test-emacs-defaults-interactively` (plain `emacs -Q` plus only a dark theme from `test-emacs-defaults-interactively.el`; does *not* load `smart-bury.el`).

Important: No need to run tests after every modification, mainly if
they are minor and simple.  Only run tests when a major modification
is performed and we're not sure about the correctness of the code.

## Architecture

Smart Bury is a single-file Emacs package (`smart-bury.el`) that wraps `bury-buffer`, `quit-window`, and `kill-current-buffer` so that repeated invocations cycle through recently-used buffers instead of landing on an arbitrary one.

Core mechanism:
- `smart-bury-commands` lists the package's own interactive commands (used to detect whether a sequence is continuing — see `smart-bury--starts-now-p` below). It starts as the three commands that never change (`smart-bury-switch-through-buffers`, `smart-bury-switch-to-other-buffer`, `smart-bury-bury-buffer`) and is extended by `smart-bury--set-wrapped-commands` with whatever `smart-bury-wrapped-commands` generates.
- `smart-bury--starts-now-p` checks `last-command` against `smart-bury-commands` to detect whether the current invocation continues a sequence or starts a fresh one.
- `smart-bury-initial-buffer` (the buffer active when a sequence started) and `smart-bury-counter` (how many buffers deep into the cycle we are) are the two pieces of global state threaded through a sequence of calls.
- `smart-bury--run-function` is the shared wrapper used by `smart-bury-bury-buffer` and every command generated from `smart-bury-wrapped-commands`: it calls the underlying Emacs function, then — unless this is a fresh sequence — switches through `smart-bury-counter` eligible buffers via `smart-bury--go-through-buffers`, keeping `smart-bury-initial-buffer` in sync with wherever the sequence actually lands.
- `smart-bury-switch-through-buffers` and `smart-bury-switch-to-other-buffer` instead call `smart-bury--go-through-buffers` directly (no underlying Emacs function to delegate to), incrementing/pinning the counter themselves.
- `smart-bury--go-through-buffers` first filters `(buffer-list)` (scoped to the selected frame when `smart-bury-same-frame` is non-nil) down to the eligible buffers (skipping the minibuffer, buffers already displayed in a window unless `allow-current`, and buffers whose name starts with `" *"`), signaling `user-error` immediately if none qualify. It then cycles through that eligible list in laps until it has collected `smart-bury-counter` buffers (wrapping around as needed — each lap is guaranteed to make progress since the eligible list is non-empty, so this always terminates), switches through all but the last, and returns the last. Preserving the lap-by-lap switching (rather than jumping straight to the final buffer) matters: those intermediate `switch-to-buffer` calls are what keep Emacs's real most-recently-used buffer order consistent with the counter, which `smart-bury-switch-to-other-buffer` relies on to land back on the original buffer after a run of `smart-bury-switch-through-buffers` calls.
- `smart-bury-quit-window` and `smart-bury-kill-current-buffer` are not hand-written `defun`s — they're generated by `smart-bury--define-wrapper`, which builds an interactive command named `smart-bury-FN` for each `FN` in the `smart-bury-wrapped-commands` defcustom (default `(quit-window kill-current-buffer)`), reusing `FN`'s own `interactive` spec (via `interactive-form`) so it accepts whatever arguments `FN` itself would. `smart-bury-bury-buffer` stays hand-written since it alone has a fixed default keybinding.
- Setting `smart-bury-wrapped-commands` (via `setopt`/Customize, not plain `setq`) runs its `:set` function, `smart-bury--set-wrapped-commands`, which regenerates the wrapper commands and keeps `smart-bury-commands` and `smart-bury-mode-map`'s dynamic remaps in sync. One subtlety that cost real debugging time: `define-minor-mode` captures `smart-bury-mode-map` *by value*, not via a live symbol lookup, so once `smart-bury-mode` is enabled, reassigning the variable (`setq`) to a new keymap silently stops taking effect — the fix is to mutate the existing keymap object in place (`setcdr`), rebuilt each time from the never-mutated `smart-bury--mode-map-base` so a command removed from the list actually loses its remap instead of it lingering. `smart-bury--set-wrapped-commands` filters out any entry with no `interactive-form` (undefined, or a plain non-interactive function) and reports it via `display-warning` rather than erroring — only the remaining valid entries get wrapped/remapped/added to `smart-bury-commands`. This matters because this function runs as the defcustom's `:set`, which `custom-initialize-reset` invokes synchronously *while `smart-bury.el` itself is loading* if a saved Customize value already existed (e.g. from a custom-file) before the `defcustom` form ran — an earlier version signaled `user-error` for a bad entry instead, which meant a single stale/renamed command left over in a user's saved config would make `(require 'smart-bury)` itself fail, aborting the whole package (and likely the rest of the caller's init file) over one unrelated wrapper.
- `smart-bury-mode` is a global minor mode (`smart-bury-mode-map`) whose *fixed* entries (`smart-bury--mode-map-base`) remap `bury-buffer` and bind `C-x M--`/`C-x _`/`C-x M-_`; the `quit-window`/`kill-current-buffer` remaps are the dynamic ones described above.
- `smart-bury-repeat-map` lets Emacs's built-in `repeat-mode` repeat a command with a single key once invoked. Every Smart Bury command — the three fixed ones plus every `smart-bury-wrapped-commands` entry — gets `repeat-map` set to it and `repeat-check-key` set to `no`, so the map arms regardless of which key actually triggered the command. Unlike `smart-bury-mode-map`, `smart-bury-repeat-map` itself is never reassigned/rebuilt by customization (only the `put` properties on each wrapper command point to it), since `repeat.el` always resolves it via a fresh `symbol-value` at repeat time — no capture-by-value issue there.

Known open issues are tracked in `IMPROVEMENTS.md` (no `buffer-live-p` guard on caller-supplied buffer lists in `smart-bury--go-through-buffers`, an unconfirmed suspected bug in `smart-bury-kill-current-buffer`, and a missing license header).

Tests in `smart-bury-tests.el` use several macros: `smart-bury-test-with-buffers` (creates fresh buffers, resets global state, always kills the buffers afterward), `smart-bury-test-with-buffer-list` (stubs `buffer-list` to a fixed set), `smart-bury-test-with-mode` (enables `smart-bury-mode` for the duration, always disabling it afterward), and `smart-bury-test-with-wrapped-commands` (temporarily customizes `smart-bury-wrapped-commands`, always restoring and regenerating the original value afterward). Note that `bury-buffer`/`quit-window` pick their target via the *selected window's* own prev/next-buffer history, not via `buffer-list` — so tests for those commands check the counter/initial-buffer bookkeeping invariant rather than the exact destination buffer. The one test that exercises the real (unstubbed) `buffer-list` MRU reordering — `smart-bury-test-switch-through-then-switch-to-other-returns-to-origin` — exists because a prior refactor of `smart-bury--go-through-buffers` passed every other test while silently breaking that invariant; the stubbed-buffer-list tests can't catch that class of regression.

`test-interactively.el` (run via `make test-interactively`) and `test-emacs-defaults-interactively.el` are separate, non-ERT files for manual sessions under `emacs -Q` (with and without the package, respectively) — not for automated testing.
