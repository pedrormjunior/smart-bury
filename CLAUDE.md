This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Run the test suite: `make test`
  (equivalent to `emacs -batch -l ert -l smart-bury.el -l smart-bury-project.el -l smart-bury-tests.el -l smart-bury-project-tests.el -f ert-run-tests-batch-and-exit`; the project tests use `smart-bury-tests.el`'s macros, so it is loaded first)
- Run a single test: `emacs -batch -l ert -l smart-bury.el -l smart-bury-project.el -l smart-bury-tests.el -l smart-bury-project-tests.el --eval '(ert-run-tests-batch-and-exit "test-name-regexp")'` (no `-f ert-run-tests-batch-and-exit` here — that would run every test and exit before the `--eval` is reached),
  or interactively via `emacsclient` (see `emacs-skills:emacsclient` — always use `emacsclient`, not `emacs`, for interactive elisp work, byte compilation, or `check-parens`).
- Lint docstrings: `make checkdoc` (runs `checkdoc-file` on `smart-bury.el` and `smart-bury-project.el`; exits non-zero if it reports any warning).
- Byte-compile with warnings as errors: `make compile` (both files, with `-L .` since `smart-bury-project.el` requires `smart-bury`; removes the `.elc` files afterward).
- Lint package metadata and Emacs-version compatibility: `make package-lint` (runs `package-lint` on both files, as MELPA does, with `package-lint-main-file` set to `smart-bury.el` so the other file is linted as part of its package, without headers of its own such as `Version`; package-lint accepts `project-buffers`, newer than 27.1, thanks to the `fboundp` check before it; uses the user's installed `package-lint` via `package-initialize`, or else installs it from MELPA into a git-ignored local `.elpa/`, as in CI).
- CI: `.github/workflows/ci.yml` runs `make test` on Emacs 27.1, 28.2, 29.4, 30.1 (and snapshot, allowed to fail), plus `make compile`, `make checkdoc`, and `make package-lint` on 30.1. Emacs 27.1 is the oldest version `Package-Requires` claims; CI is the only place it's actually tested.
- Try the package interactively, isolated from the user's own init file: `make test-interactively` (loads `smart-bury.el` and `test-interactively.el` under `emacs -Q`; see that file for what it sets up — enabling `smart-bury-mode`/`repeat-mode`, a repeat binding for `smart-bury-kill-current-buffer`, `smart-bury-project.el` with `smart-bury-project-bury-buffers` on `C-x p M--` and `smart-bury-project-raise-buffers` on `C-x p -`, throwaway buffers `A` to `E`, and `smart-bury.el` and `smart-bury-project.el` opened as a project's buffers; it starts Emacs from `$HOME`, so the other buffers are outside the repository's project).
- Explanatory animation (Manim, in `demo/`): `make demo-check` (replays the README cases on the Python model and checks the subtitles' translations), `make demo-preview` (fast 480p15 render into `demo/smart-bury-demo-preview.mp4`), `make demo` (final 1080p60 render into `demo/smart-bury-demo.mp4`, ~3 minutes). `demo/` is a standalone `uv` project (`demo/pyproject.toml`, Python 3.13 since `kokoro-onnx` requires < 3.14, Manim from PyPI); `uv run` creates `demo/.venv` on first use.
- Short intro animation (`demo/smart_bury_intro.py`, ~3:30): `make intro-check` (Manim `--dry_run`: runs the scene without rendering, so every storyboard step's `expect`ed buffer order is asserted against the model; `write_ttml`/`ttml_text`), `.ttml`, the format whose colors YouTube keeps, though it ignores fonts and backgrounds, so keys get a color of their own, plus their translations next to them, e.g. `demo/smart-bury-intro-<quality>.pt-BR.ttml` and `.pt-BR.srt`, for each of `LANGUAGES` in `demo/translations.py` (`write_ttml`, `write_srt`), with the English timing: a caption changed or added needs its entry in `TRANSLATIONS`, or it stays in English with a warning, and `translations.py`, run by `make demo-check`, verifies each entry's caption exists in the scene and its translations keep its markup; a narrated render also gets a dubbed audio track per language, e.g. `demo/smart-bury-intro-<quality>.pt-BR.wav`, for YouTube's multi-language audio: `demo/dub.py`, run by `make intro` after the render so a failure can't lose it, speaks each translation with the voice in `DUB_VOICES`, the key names in `KEY_WORDS`, and the phonemes in `SPOKEN_PHONEMES` (`phonemes_with`; for words like "Bury" no Portuguese spelling can say, as Portuguese has no English "r"; speech only, subtitles are unaffected), placing it at the English caption's speech start (`write_speech_cues`, `media/dub/cues.json`), or `GAP` after the previous clip if that overruns, in a track as long as the video, raised to `INTRO_LOUDNESS` with two-pass `loudnorm` plus the gain left, as `loudnorm` alone falls short on tracks with long silences; its audio raised with ffmpeg's `loudnorm` to `INTRO_LOUDNESS`, -14 LUFS, since Kokoro comes out around -26 and YouTube doesn't turn quiet videos up; narrated in `VOICE`, by default the blend `am_michael:0.7,bm_george:0.3` (`NAME:WEIGHT,...`: `Narrator.style` takes the weighted mean of the voices' style vectors, weights normalized), a single voice such as `make intro VOICE=am_michael`, or silent with `make intro VOICE=`; ~3–4 minutes at 480p15, ~8 at 1080p60). Narration (`demo/narration.py`) is local text-to-speech with Kokoro through `kokoro-onnx`: `make voice-models` downloads the full-precision `kokoro-v1.0.onnx` and `voices-v1.0.bin` once into the git-ignored `demo/voice-models/`, and `make voice-samples` writes a few captions in candidate voices into `demo/voice-samples/`. `make voice-model-timed` (`demo/kokoro-export/build.sh`, its own Python 3.12 uv project with CPU-only PyTorch) exports the original Kokoro weights to `demo/voice-models/kokoro-v1.0-timed.onnx` with a durations output, enabling continuous synthesis and phoneme timings, which the scene uses through `Narrator.time_at` (`caption_time_at`): `cue()` waits for a phrase, each key press waits until the caption's narration names its keys (`land`), and a buffer's box expands and contracts, in its own colors, as its name is said, starting 0.45 s earlier (`pulse_updater`, through an opaque copy following the box, so the box can move meanwhile); without it, `narration.py` falls back to the prebuilt model and `cue()` estimates. `demo/README.md` documents the build, its manual equivalent, and troubleshooting; `make voice-model-check` and `make voice-model-clean` check and remove it. `say()` is the only hook: with `SMART_BURY_VOICE` set, each caption waits for the previous one's speech to end, then its clip (`spoken()` turns key and symbol markup into words; `speech=` overrides it). Buffer names in captions are written in double quotes (`'back to "A".'`): `parse_rich` shows them unquoted in the buffer's color, while narration and subtitles keep the quotes, which make Kokoro say the letter rather than the article "a"; a bare capital, e.g. a sentence-initial article, stays plain is added with `add_sound`, cached in `demo/media/voice/`; every caption also becomes a subtitle through Manim's `add_subcaption`. On the title, the cards, and the outro, which already show their text, the narration has no on-screen caption (`say(visible=False)`) but is still spoken and subtitled. Clips go straight to `self.renderer.file_writer.add_sound`, not `Scene.add_sound`, which drops a sound added right after an animation reused from Manim's cache (the renderer's skipping state lasts until the next animation starts). Narrated renders, and `make intro-narration` (a dry run), print per caption how long its part lasts without narration, how long its speech lasts, and the difference. `make intro-part N=START,END` renders a range of animations at 480p15 into `demo/smart-bury-intro-part.mp4`. `make intro-thumbnail` writes a 1280x720 frame of the `INTRO_QUALITY` render, at `THUMBNAIL_TIME` (the "smart" bury), to `demo/smart-bury-intro-thumbnail.png`, for YouTube. `make intro-play` plays the `INTRO_QUALITY` render in mpv with its dubbed tracks, `#` cycling through them (`AID=2` starts on Portuguese).

## Architecture

Smart Bury is an Emacs package that wraps `bury-buffer`, `quit-window`, and `kill-current-buffer` so that repeated invocations cycle through recently-used buffers instead of landing on an arbitrary one. Its core is `smart-bury.el`, the main file (the only one with `Version` and `Package-Requires`); `smart-bury-project.el` adds commands for a project's buffers (see below).

Core mechanism:
- `smart-bury--commands` lists the package's own interactive commands (used to detect whether a sequence is continuing — see `smart-bury--starts-now-p` below). It starts as the three hand-written basic commands (the constant `smart-bury--basic-commands`: `smart-bury-switch-through-buffers`, `smart-bury-switch-to-other-buffer`, `smart-bury-bury-buffer`) and is extended by `smart-bury--set-wrapped-commands` with whatever `smart-bury-wrapped-commands` generates, and with `smart-bury--extra-commands`: the commands of Smart Bury's other files, each registered when its file loads with `smart-bury--register-command`, which also makes it repeatable. Keeping them in their own list is what lets them survive the rebuild of `smart-bury--commands` whenever `smart-bury-wrapped-commands` is set (`smart-bury-test-register-command` guards this).
- `smart-bury--starts-now-p` (pure) checks `last-command` against `smart-bury--commands` to detect whether the current invocation continues a sequence or starts a fresh one; `smart-bury--maybe-start-sequence` is what the commands call — on a fresh start it also records the current buffer as `smart-bury--initial-buffer`. `smart-bury--maybe-restart-sequence` adds the other reset condition used by the two switch commands: being back on the initial buffer.
- `smart-bury--initial-buffer` (the buffer active when a sequence started) and `smart-bury--counter` (how many buffers deep into the cycle we are) are the two pieces of global state threaded through a sequence of calls.
- `smart-bury--run-function` is the shared wrapper used by `smart-bury-bury-buffer` and every command generated from `smart-bury-wrapped-commands`: it calls the underlying Emacs function, then — unless this is a fresh sequence — switches through `smart-bury--counter` eligible buffers via `smart-bury--go-through-buffers`, keeping `smart-bury--initial-buffer` in sync with wherever the sequence actually lands.
- `smart-bury-switch-through-buffers` instead calls `smart-bury--go-through-buffers` directly (no underlying Emacs function to delegate to) and increments the counter itself. `smart-bury-switch-to-other-buffer` calls `smart-bury--walk-back` on the first `(1- smart-bury--counter)` buffers from `smart-bury--select-buffers`, landing on the first of them (the initial buffer, or the "other" one on a fresh sequence), then pins the counter to 2. Both read the list through `smart-bury--other-buffers`, which records the current buffer with `(select-window (selected-window))` before taking the `cdr`: `previous-buffer` and friends change the window's buffer through `set-window-buffer`, which never records it (`record_buffer`'s only caller is `select_window`), so the current buffer may not be first, and a plain `cdr` would drop the actual first buffer. Recording rather than just removing the current buffer also makes it the second buffer once a sequence leaves it, which the counter relies on (`smart-bury-test-switch-through-from-unrecorded-buffer` guards this).
- The cycling is built from two helpers. `smart-bury--select-buffers` filters a buffer list (normally `smart-bury--buffer-list`, scoped to the selected frame when `smart-bury-same-frame` is non-nil) down to the eligible buffers via `smart-bury--eligible-p` (skipping dead buffers, the minibuffer, internal buffers whose name starts with a space, and buffers already displayed in a window, except the current buffer when `allow-current` and, when it isn't current, the initial buffer, or any buffer when the `smart-bury-include-displayed-buffers` option is non-nil — the initial buffer must stay eligible while also shown in another window, e.g. right after a split, since a sequence counts it as the first buffer once it leaves it; dropping it made every later call skip a buffer and `smart-bury-switch-to-other-buffer` miss the origin, which `smart-bury-test-sequence-with-initial-buffer-in-other-window` guards), signals `user-error` if none qualify, and returns the first N, wrapping around modulo their count. `smart-bury--walk-back` switches to each buffer of a selection in reverse order, so its first buffer ends up current. Every switch Smart Bury makes, intermediate or final, goes through `smart-bury--switch-to-buffer`, which binds `switch-to-buffer-obey-display-actions` to nil: obeying a buffer's display action (e.g. a `display-buffer-alist` rule deleting other windows) mid-sequence would apply it to every buffer merely passed through, and could move the sequence to another window (`smart-bury-test-switching-ignores-display-actions` guards this). `smart-bury--go-through-buffers` selects `smart-bury--counter` buffers, walks back through all but the last, and returns the last for the caller to switch to. The intermediate switches (rather than jumping straight to the final buffer) matter: they are what keep Emacs's real most-recently-used buffer order consistent with the counter, which `smart-bury-switch-to-other-buffer` relies on to land back on the original buffer after a run of `smart-bury-switch-through-buffers` calls.
- `smart-bury-quit-window` and `smart-bury-kill-current-buffer` are not hand-written `defun`s — they're generated by `smart-bury--define-wrapper`, which builds an interactive command named `smart-bury-FN` for each `FN` in the `smart-bury-wrapped-commands` defcustom (default `(quit-window kill-current-buffer)`), reusing `FN`'s own `interactive` spec so it accepts whatever arguments `FN` itself would. The spec is looked up (via `interactive-form`) and evaluated only when the wrapper is called, by `smart-bury--interactive-args`, so `FN` need not be defined when the wrapper is (e.g. a command from a package loaded after Smart Bury); calling the wrapper while `FN` is still not a command signals `user-error`, before any sequence state changes. `smart-bury-bury-buffer` stays hand-written as one of the three basic commands, whose keys come from `smart-bury-keys`.
- Keymaps are split into a user-owned public map and a package-owned parent: `smart-bury-mode-map` (parent `smart-bury--mode-map-generated`) and `smart-bury-repeat-map` (parent `smart-bury--repeat-map-generated`). The public maps start empty and are never touched by the package, so a user's own `define-key` into them survives any customization. `smart-bury--rebuild-keymaps` rebuilds both parents *in place* (`setcdr`) from `smart-bury-prefix-key`, `smart-bury-keys` (alist of COMMAND . single KEY; the key goes after the prefix in the mode map and alone in the repeat map), and `smart-bury--valid-wrapped-commands` (one `[remap FN]` each), plus the fixed `[remap bury-buffer]`. In-place mutation matters because `define-minor-mode` captures `smart-bury-mode-map` *by value*, not via a live symbol lookup — reassigning a keymap variable silently stops taking effect once the mode is enabled (this cost real debugging time). A `smart-bury-keys` entry whose key isn't a single event is skipped with `display-warning`.
- The three keymap options' (`smart-bury-prefix-key`, `smart-bury-keys`, `smart-bury-wrapped-commands`) `:set` functions end in `smart-bury--rebuild-keymaps` (`smart-bury--set-and-rebuild` for the two key options). Since `custom-initialize-reset` runs `:set` *during load*, before later defcustoms exist, the rebuild is guarded to do nothing until all three options are `boundp`; `smart-bury-wrapped-commands` is deliberately defined last so its `:set` triggers the first full build. (`:set-after` would not help here — it only orders `custom-set-variables`, not defcustom evaluation.)
- Setting `smart-bury-wrapped-commands` (via `setopt`/Customize, not plain `setq`) runs its `:set` function, `smart-bury--set-wrapped-commands`, which regenerates the wrapper commands, `smart-bury--commands`, and `smart-bury--valid-wrapped-commands`, then rebuilds the keymaps. An entry that isn't defined yet is wrapped all the same, without a warning. Only an entry known not to be a command (nil, a non-symbol, or a defined but non-interactive function) is filtered out by `smart-bury--valid-commands` (shared with `smart-bury-repeatable-commands`) and reported via `display-warning` rather than erroring — only the remaining valid entries get wrapped/remapped/added to `smart-bury--commands`. This matters because this function runs as the defcustom's `:set`, which `custom-initialize-reset` invokes synchronously *while `smart-bury.el` itself is loading* if a saved Customize value already existed (e.g. from a custom-file) before the `defcustom` form ran — an earlier version signaled `user-error` for a bad entry instead, which meant a single stale/renamed command left over in a user's saved config would make `(require 'smart-bury)` itself fail, aborting the whole package (and likely the rest of the caller's init file) over one unrelated wrapper. The check uses `commandp`, not `interactive-form`: the latter loads an autoloaded command's library, which would load every wrapped package as soon as Smart Bury loads. The option's `:type` is `(repeat symbol)`, not `(repeat function)`, which would reject an undefined entry (making `setopt` warn).
- `smart-bury-repeatable-commands` (default `(split-window-below split-window-right)`) lists commands that are neither wrapped nor added to `smart-bury--commands` (so they don't continue a sequence), but arm `smart-bury-repeat-map` so a new sequence can start with a single key. The rule of thumb between the two lists: commands that get rid of the current buffer (bury, quit, kill) are wrapped; those that don't are repeatable. `smart-bury--apply-repeatable-commands`, run by its `:set` (`smart-bury--set-repeatable-commands`) and by `smart-bury-mode` on every toggle, first restores the `repeat-map`/`repeat-check-key` properties saved in `smart-bury--repeatable-saved` (most recent first, and only where the property still holds Smart Bury's value, so a repeat map a package set meanwhile isn't clobbered), then, only while the mode is on, saves and replaces them for each entry of `smart-bury--valid-repeatable-commands`. Unlike the Smart Bury commands' own properties, these are scoped to the mode, since they modify other packages' commands, some of which have a repeat map of their own (e.g. `other-window`, `undo`, `next-buffer`). Its `:set` doesn't touch the keymaps, so it is defined before `smart-bury-wrapped-commands`, which stays last.
- `smart-bury-add-command` (autoloaded, defined after `smart-bury-wrapped-commands`) adds a command to `smart-bury-repeatable-commands` or `smart-bury-wrapped-commands` by key, like `describe-key`. Its interactive spec, `smart-bury--read-command-to-add`, reads a key with `read-key-sequence-vector` and takes `(key-binding key t)` *with* remapping, since the remapped command is the one that runs, the `this-command` that `repeat-mode` and `smart-bury--report-repeatable` see. Before any question it rejects with `user-error` an undefined key, a non-symbol binding (lambda, keyboard macro), a Smart Bury command (incl. a remap target such as `smart-bury-quit-window`, and any command named `smart-bury-...`, e.g. one autoloaded from a Smart Bury file not loaded yet, hence not registered), and a command in either list already (e.g. `quit-window` read with the mode off). It then asks which list (`read-multiple-choice`, `r`/`w`), for the repeatable one whether to replace a `repeat-map` of the command's own (wrapping leaves the command's properties alone), and whether to save. The command itself only appends to the list and sets it, with `customize-save-variable` when SAVE is non-nil (writing to `custom-file`), else `customize-set-variable` (not `setopt`, which needs Emacs 29). There is deliberately no removal command. Tests stub `read-key-sequence-vector`, `read-multiple-choice`, `y-or-n-p`, and `customize-save-variable`, so they never write `custom-file`.
- `smart-bury-mode` is a global minor mode whose default bindings are `C-x _`/`C-x M-_`/`C-x M--` (from `smart-bury-prefix-key` + `smart-bury-keys`), plus the remaps described above; toggling it also applies or restores `smart-bury-repeatable-commands`.
- `smart-bury-repeat-map` lets Emacs's built-in `repeat-mode` repeat a command with a single key once invoked. Every Smart Bury command — the three fixed ones, the registered `smart-bury--extra-commands`, plus every `smart-bury-wrapped-commands` entry — gets `repeat-map` set to it and `repeat-check-key` set to `no` (via `smart-bury--make-repeatable`), as does every `smart-bury-repeatable-commands` entry while the mode is on, so the map arms regardless of which key actually triggered the command.
- Each command reports its position in the sequence, as "POSITION/TOTAL" from `smart-bury--position` (depth counting the initial buffer as 1, out of the eligible buffers, current included; e.g. "Smart Bury: 3/7"), through the `smart-bury--report` macro (a macro so `called-interactively-p` is evaluated in the calling command): only when called interactively and `smart-bury-messages` is non-nil, with the "Smart Bury:" label in face `smart-bury-message-prefix`. While the mode is on, `smart-bury--report-repeatable`, on `post-command-hook` at depth -50 so it runs before `repeat-mode`'s `repeat-post-hook` (which appends its hint to the current message) whichever mode is enabled first, reports position 1 after a `smart-bury-repeatable-commands` entry, only with `repeat-mode` on and when the command left no message of its own; it binds `smart-bury--initial-buffer` to the current buffer so the total is the one a fresh sequence will see.
- `smart-bury--bury-buffers` buries a set of buffers, the current one included, the way `smart-bury-bury-buffer` buries the current one alone, for commands such as `smart-bury-project-bury-buffers`. It works in the sequence's order, the one Emacs's list would have had the user never left the initial buffer: the current buffer is `smart-bury--depth` deep (1 on the initial buffer, else `smart-bury--counter`), after the initial buffer and the buffers passed on the way, the first `(1- depth)` of `smart-bury--other-buffers`. It walks back through those passed, so Emacs's list follows that order, then buries the set's buffers with `bury-buffer-internal`, most recent first, so they keep their order at the end of the list (also in the frame's `buffer-list`, whose buried part is reversed). The buried buffers passed on the way are no longer on it: the counter becomes one more than the number of buffers left among those passed, and it then selects as `smart-bury--go-through-buffers` does, the first of the selection becoming the initial buffer. When no eligible buffer left follows those passed, the counter goes back to 1 instead of running into the buried buffers: the user expects e.g. `_` from `A` to `B`, then burying `B`'s project, the only buffer outside it being `A`, to land on `A`, not to stay on `B` (`smart-bury-test-bury-buffers-none-left-after`). The same rule covers a wrapped-around selection of those passed (counter past the eligible buffers), whose repeated buffers count twice to the same effect, so no `seq-uniq` is needed. When every buffer is in the set, the order doesn't change and the sequence lands on its initial buffer (on a fresh call, the current one): the user agreed that's the "natural next buffer" there, rather than skipping the current buffer, which would make repeated calls toggle between two buffers. Each case of its docstring has a `smart-bury-test-bury-buffers-*` test.
- A command that can't do its job (e.g. `smart-bury-project-bury-buffers` outside a project) uses the `smart-bury--do-nothing` macro: it changes nothing, but a fresh call still starts a sequence (initial buffer and counter 1), so the next Smart Bury command doesn't continue a stale one; then it reports the reason after the position, `Smart Bury: 1/80 (not in a project)`, or alone when `smart-bury-messages` is nil: reasons are reported regardless, like `user-error`s. `smart-bury--switch-blocked-reason` is one such reason: in a minibuffer or strongly dedicated window, `switch-to-buffer` called from Lisp pops the buffer into another window, so a command that would bury first and switch last checks it before changing anything.
- `smart-bury--raise-buffers` is the converse: it raises a set of buffers, the current one included, to the top of the list by burying every other buffer, most recent first (`bury-buffer-internal`; the user chose this over switching through the set, which would show each buffer in the selected window, fill its `window-prev-buffers`, and fail in dedicated windows), skipping internal buffers, and stays on the current buffer. It needs no walk-back: mid-sequence, the list is already in the sequence's order but for the current buffer, first, which stays there. The order is the sequence's (the user's choice, over restarting the sequence from the current buffer): the counter becomes one more than the number of the set's buffers passed on the way, the first of which becomes the initial buffer (the current one when none was passed), e.g. `C-x _ _` from `A` to `C`, then raising `{A, C, E}`, leaves `C A E B D`, `C` 2 deep, so `M-_` goes back to `A` and `_` on to `E`. Here `seq-uniq` does matter: a wrapped-around selection of those passed would count a repeated buffer twice (`smart-bury-test-raise-buffers-counter-past-buffers`).
- `smart-bury-project.el` (`smart-bury-project-bury-buffers` and `smart-bury-project-raise-buffers`, autoloaded, with no default key: users bind them, e.g. `C-x p M--` and `C-x p -`, and `smart-bury-keys` stays for the basic commands) gets the project's buffers from `smart-bury-project--buffers`, `project-buffers` of `project-current`, which returns a string instead when there are none: `"not in a project"`, or `"needs Emacs 28"` without `project-buffers`. The commands pass them to `smart-bury--bury-buffers` or `smart-bury--raise-buffers` and report `Smart Bury: 3/80 (buried 5)` or `(raised 5)` (internal buffers not counted, `smart-bury-project--count`), or pass the reason to `smart-bury--do-nothing`: the bury's own or `smart-bury--switch-blocked-reason`'s; the raise's own or `"minibuffer window"`, since it switches no buffer, so a dedicated window doesn't stop it. Raising applies to the current buffer's project only: raising a buried one takes going to one of its buffers first (selecting a project is a README TODO). The file ends by registering the commands.

Tests in `smart-bury-tests.el` (and `smart-bury-project-tests.el`, which requires it) use several macros: `smart-bury-test-with-buffers` (creates fresh buffers, resets global state, always kills the buffers afterward), `smart-bury-test-with-buffer-list` (stubs `buffer-list` to a fixed set), `smart-bury-test-with-mode` (enables `smart-bury-mode` for the duration, always disabling it afterward), `smart-bury-test-with-wrapped-commands` (temporarily customizes `smart-bury-wrapped-commands`, always restoring and regenerating the original value afterward), `smart-bury-test-with-keys` (the same for `smart-bury-prefix-key` and `smart-bury-keys`), and `smart-bury-test-with-repeatable-commands` (the same for `smart-bury-repeatable-commands`; its tests list uninterned `make-symbol` commands, so the properties they get never leak into other tests). Note that `bury-buffer`/`quit-window` pick their target via the *selected window's* own prev/next-buffer history, not via `buffer-list` — so tests for those commands check the counter/initial-buffer bookkeeping invariant rather than the exact destination buffer. The one test that exercises the real (unstubbed) `buffer-list` MRU reordering — `smart-bury-test-switch-through-then-switch-to-other-returns-to-origin` — exists because a prior refactor of `smart-bury--go-through-buffers` passed every other test while silently breaking that invariant; the stubbed-buffer-list tests can't catch that class of regression. `smart-bury-test-with-case-only` combines both: the five README-case buffers, in the real `buffer-list` order, with `buffer-list` filtered to report only them, so burying reorders it for real while the session's other buffers (`*scratch*`, ...) never come up once the case's buffers outside the set are used up. The project tests stub the lookup, `smart-bury-project--buffers` (`smart-bury-project-test-with-case`), never relying on real project detection: CI and local runs happen inside a git checkout, which is a project, and on Emacs 27, without `project-buffers`. Only the lookup's own tests use the real thing, skipping themselves where it can't apply (`skip-unless`).

The animation in `demo/` is driven by `demo/smart_bury_sim.py`, a pure-Python model whose methods mirror `smart-bury.el`'s functions one-to-one (`blist[0]` is current, shown in the selected window; after `split_window`, `others` holds the buffers shown in the other windows, which only affects eligibility and `other_buffer`; `report` is what the last command reported, e.g. `"2/5"`, mirroring `smart-bury--position`, and assumes `repeat-mode` is on; vanilla bury/quit modeled as "move to the end, show the new head"). Its self-check replays README Cases 1–7 and "Why is it smart?" with the same expectations as the `smart-bury-test-readme-*` tests, so any change to the Elisp algorithm should be mirrored there. `demo/smart_bury_demo.py` (scene `SmartBuryDemo`) only draws the model's recorded steps: buffer boxes slide between slots of the "list of all buffers", the window, keys, counter, and "initial" marker update together in `press`. The rendered MP4s are not committed yet; `demo/` is outside the MELPA package (the recipe, not in this repository, must list `:files ("smart-bury.el" "smart-bury-project.el")`: MELPA's default would also take `test-interactively.el` and `test-emacs-defaults-interactively.el`).

`demo/smart_bury_intro.py` (scene `SmartBuryIntro`) is the short introduction: title cards for the three basic and the wrapped commands, then one continuous five-buffer session (vanilla `C-x b` with minibuffer typing, switching through to the last, switching to the other buffer, breaking a sequence, burying every buffer in turn, the "smart" bury, and `C-x 3 _ _` with the initial buffer still shown in the other window). Its layout differs from the long demo: an Emacs frame at the top (split in two by `C-x 3` at the end) with a minibuffer (showing Smart Bury's message and repeat-mode's hint, e.g. `Smart Bury: 2/5 [Repeat with: _, M-_, M--]`, after Smart Bury commands and `smart-bury-repeatable-commands`, or the `C-x b` prompt), the "list of all buffers" below it with both the current and the other buffer marked (and, once split, the right window's buffer), captions at the bottom. It shares nothing with `smart_bury_demo.py`, which it leaves untouched. Each step passes `expect=` with the buffer order it should produce, and the model raises on a mismatch; the storyboard was also replayed against the real package in batch Emacs (with only the demo's buffers eligible) and agreed at every step. The model's `switch_to_buffer` is vanilla `switch-to-buffer`, so it ends a sequence, and `other` mirrors `(other-buffer)`. Note for storyboards: switching through to the last buffer (counter equal to the number of eligible buffers) and then burying it immediately lands on that same buffer. This is expected, not a bug: the bury moves it to the end of the list, and the counter still points to the last position. To show a bury returning to the initial order, work on that buffer first, so the bury is a fresh one.

`test-interactively.el` (run via `make test-interactively`) and `test-emacs-defaults-interactively.el` are separate, non-ERT files for manual sessions under `emacs -Q` (with and without the package, respectively) — not for automated testing.
